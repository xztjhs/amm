# AMM 开发经验沉淀（截至 v1.9）

> 记录踩过的坑与可复用的做法，避免重复排查。
> 面向后续接手的人（或未来的自己）。

---

## 一、环境与部署

### 1. 容器名是 `AMM`，不是 `amm`
`docker restart amm` 会报 `No such container`。正确的是 `docker restart AMM`。

### 2. 代码目录挂载，改代码不用重建镜像
```
/path/to/amm       -> /amm
/path/to/models -> /models
/path/to/amm-engines      -> /opt/amm-engines
```
升级流程：`git pull` → `docker restart AMM`。

### 3. 生产目录部署更新
宿主机没有配置 git 凭据时，直接 `git pull` 会要求输入用户名。
推荐用只读部署 key 或凭据助手，然后：
```bash
git pull origin master --ff-only
```
若提示本地有改动被挡：确认是无意修改后 `git checkout -- <file>` 再拉。
**注意**：生产目录里 `backend/config/models_config.yaml` 常有本地改动（节点名等），
不要随手 checkout 掉。

### 4. 镜像不含 CUDA 运行时库
`Dockerfile.unraid` 虽然用 RPM 装了 libcublas，但**生产容器是旧镜像**，
其 `/usr/local/cuda-13.2/lib64` 是容器写层里后来装的。
新建容器（如测试环境）会报：
```
libcublas.so.13: cannot open shared object file
```
从能跑的容器导出并挂载：
```bash
docker exec AMM sh -lc "cd /usr/local/cuda-13.2 && tar -chf - lib64" > lib.tar
tar -xf lib.tar -C /path/to/cuda/
# 运行时：-v /path/to/cuda/lib64:/usr/local/cuda-13.2/lib64:ro
```
**必须用 `tar -chf`**：`docker cp` 不跟随符号链接，只会复制出一堆断链。

### 5. 容器退出无人知晓 —— 根因是 RestartPolicy
2026-11-16 两次「容器挂了」：
- 11:31 `Exit=0`：被正常 stop
- 14:10 `Exit=255`：异常退出后无人处理

排查结论：宿主机 19:27 重启过（`uptime` / `last reboot`），
容器 `RestartPolicy=no` → 不回来。
`/var/log/syslog`、`journalctl`、`dmesg` 在 Unraid 上基本查不到有价值的记录，
**不要在这上面浪费时间**，直接看 `docker inspect` 的 ExitCode 与宿主机 uptime。

修复：`docker update --restart unless-stopped AMM` + Dockerfile 加 HEALTHCHECK。

## 二、后端

### 6. `/api/engines/installed` 曾是 7-13 秒
`installed_versions()` 对每个引擎目录 `rglob("*")` 累加体积，
沙箱里合计 ~19 万文件（vLLM 8.9 万 / diffusers 4.6 万 / ST 4 万），且无缓存。
而启动向导每渲染一次就调它。

修复：以 `目录路径 + mtime` 为键缓存体积；启动时后台线程预热。
效果：**7-13s → 3ms**。

### 7. 鉴权判定必须单一来源
中间件原来只看 `default_key` 是否存在，而 `router.authenticate()` 还看
`auth_enforced` 和虚拟 Key。两条路径给出矛盾结果：
- 清了默认 Key 但仍 401（因为还有虚拟 Key / auth_enforced）
- 「关闭鉴权」后还是 401

修复：中间件统一为 `if not dk and not enforced: 放行`。
`auth_enforced` 是唯一开关，虚拟 Key 存着不等于必须拦截。

### 8. 「吊销完最后一个 Key」不会关闭鉴权 —— 这是刻意的
`revoke_key` 不重置 `auth_enforced`，否则任何持有旧 Key 的客户端
会突然获得无鉴权访问（安全退化）。
要退回免鉴权必须走 Settings 的「完全关闭鉴权」。
**改这个行为会被 `test_router.py::test_revoke_key` 拦住**，说明是刻意设计。

### 9. 本地实例调用历史要手动记
`record_call` 只在 provider 转发路径里调用。
`/v1/embeddings`、`/v1/rerank` 曾经完全不写调用历史（Log Center 看不到）。
新增 `_record_local_call` 后，chat/embeddings/rerank 三条路径都记。

### 10. launch 返回 running ≠ 端口可用
llama-server 进程起来到端口 accept 之间有几百毫秒到几秒的窗口，
客户端此时请求会拿到 500/连接失败。
修复：`wait_until_ready()` 用 `asyncio.open_connection` 轮询端口，
`launch` 返回带 `ready` / `ready_wait_ms`。

## 三、前端

### 11. app.js 拆分：`window.xxx = xxx` 是最大的坑
把函数搬到新模块后，core 里残留的 `window.lcExport = lcExport;`
会因为 `lcExport` 已不在作用域而抛 `ReferenceError`，
**整个 IIFE 中断，init 不执行，页面一片空白**。

症状：所有面板 `visible=false`，`offsetHeight=0`，但 HTTP 接口全 200。
排查手段：监听 `pageerror`，不要只看 console.error。

拆分时的检查清单：
1. 模块内定义的函数 → 导出移到模块
2. core 里对这些函数的**裸调用** → 改成 `window.xxx()`
3. 模块需要的 core 工具（apiGet/toast/escapeHtml）→ 显式从 window 借
4. 模块之间共享的可变状态（engineCatalog）→ 各自持有或走 window

### 12. 静态资源要带版本号
`js/app.js?v=1.9` → 升级后浏览器可能还用旧缓存。
每次前端有实质改动，把版本号一起升（现在是 `?v=2.0`）。

### 13. 内联 onclick 依赖 window 挂载
HTML 里 `onclick="window.fmInit()"` 要求函数必须 `window.xxx = ...`。
新写的模块记得补导出，否则点击「无反应」且控制台报 `not a function`。

### 14. 品牌/标题同步要放在 init 里
`applyBrand()` 只在「保存时」调用是不够的 —— 刷新后页面又回到默认值。
必须在 `init()` 里先 `loadBrand()`，且要**早于其它渲染**。

## 四、测试

### 15. E2E 用例必须按业务依赖排序，不能按字母序
`R`（管理实例）依赖 `W`（创建实例）；破坏性用例（删实例/重启服务）
如果按字符串排序会插到中间，把后续用例全带塌。
`runner.py` 里用 `ORDER_GROUPS` 显式定序，破坏性用例永远最后。

### 16. 全屏遮罩会让后续所有点击超时
帮助弹窗用 `display:flex`（不是 `.active` 类），
前一个用例没关掉，后面全部 `Page.click: Timeout 30000ms`。
`need_page()` 里统一清理残留弹窗。

### 17. 用例间状态污染是最大时间黑洞
实际踩到的：
- 签发的虚拟 Key 残留 → 后续 `/v1/*` 全 401
- 默认 Key 残留 → 同上
- **provider 的 base_url 被测试改写成 `api.openai.com`** →
  真实 Key 发到 OpenAI，返回 401 且报错信息指向 OpenAI，极难定位

对策：
- 破坏性/鉴权类用例跑完立刻 `restore_auth()`
- 改 provider 配置的用例必须保存并恢复原 `base_url`
- 诊断时把 `provider_base_urls` 一起打进 evidence

### 18. 区分 401 来源
同一个 401 可能来自：
1. AMM 自己的鉴权中间件 → `{"type":"auth_error"}`
2. 上游 provider → `{"type":"upstream_error"}` 且 message 里有对方报错

**先看响应体的 `type` 字段**，不要盲改代码。

### 19. 页面级断言要等真实渲染完成
500ms 轮询让 `networkidle` 永不触发。
用 `domcontentloaded` + `wait_for_selector` + 轮询具体元素，
例如模版列表要等到 `.tpl-card` 数量 ≥10。

## 七、从零安装 ATT 实测（2026-11-17）

用**纯净 amm:rocky9-cu132 镜像** + **v1.9 代码** 从零安装，暴露了 8 个问题，
全部已修。这是「用户实际安装」路径的真实体检。

### 7.1 安装必踩的坑（按出现顺序）

| # | 报错 | 根因 | 修复 |
|---|---|---|---|
| 1 | `Unable to find a match: cuda-toolkit-12-6` | 镜像已预装 CUDA 13.2，仓库无 12-6 包名 | 检测已装则跳过；未装才试 13-2→12-6 |
| 2 | `curl-minimal conflicts with curl` | Rocky9 自带 curl-minimal | 安装列表去掉 curl（用 wget） |
| 3 | nvcc `--error 0x7f` | 缺 nvvm 前端 `cicc` | install.sh 自检 + cuda_components.sh |
| 4 | `CMAKE_DETERMINE_COMPILER_ID` 失败 | gcc 11.5 与 CUDA 13.2 不兼容 | 装 gcc-toolset-12 |
| 5 | `CUDA::cublas target not found` | 缺 libcublas（.so / .so.13 / 真实版本三件套） | 整组拷贝 + 建链接 |
| 6 | `cublas_v2.h: No such file` | 缺 libcublas-devel 头文件 | 拷 include/*.h |
| 7 | `CUDA::cudart includes non-existent path .../cccl` | 缺 CCCL 头文件 | 下 cccl-src 并铺开 |
| 8 | `cp: 'x' and 'x' are the same file` → set -e 中止 | 代码已在 /amm，源=目标 | realpath 比较后跳过 |

### 7.2 最隐蔽的一个：GPU 静默退回 CPU

**现象**：
- `ldd llama-server` 显示链接了 libcudart / libcublas ✓
- `llama-server --list-devices` 能列出 `CUDA0: RTX A5000` ✓
- 但跑起来 `nvidia-smi` 看不到该进程，日志里连一行 CUDA 都不打 ✗

**根因**：安装脚本只 `cp llama-server`，没拷 ggml 的**动态后端库**
（`libggml-cuda.so` / `libggml-cpu.so` / `libggml-base.so`）。
这些是运行时 dlopen 的，缺了就静默退回 CPU，不报错。

**教训**：判断「是不是 CUDA 构建」不能只看 `--list-devices`，
必须看 `nvidia-smi --query-compute-apps` 里有没有这个 PID。

修复：`cp -a build/bin/*.so*` 到安装目录与 `/usr/local/bin`，并 `ldconfig`。

### 7.3 容器内没有 docker CLI

`cuda_components.sh` 原本想「从现成 AMM 容器拷贝 CUDA 组件」，
但脚本是在**容器内**跑的，容器里没有 docker。

修复：优先用**宿主机预置的组件包**（挂载到 `/opt/cuda-bundle`），
其次才回退 docker / 官方源下载。bundle 结构：

```
/opt/cuda-bundle/
├── bin/cicc                      nvvm 前端
├── nvvm-lib/libnvvm.so*          nvvm 运行库
├── lib64/libcublas*.so*          cublas / cublasLt / nvblas
└── include/
    ├── cublas*.h                 头文件
    └── cccl/                     cub / thrust / libcudacxx
```

制作方法（在能跑的容器上做一次）：
```bash
docker exec AMM sh -c "cd /usr/local/cuda-13.2/lib64 && tar -chf - \
  libcublas.so.13.4.1.3 libcublasLt.so.13.4.1.3 libnvblas.so.13.4.1.3" \
  > bundle/lib64/libs.tar
# 同样导出 include/、nvvm/bin、nvvm/lib64
```
注意必须 `tar -ch`（`docker cp` 不跟随符号链接）。

## 八、分支策略（2026-11-17 统一）

### 8.1 历史问题

曾经同时存在 `master` 与 `v1.0` 两个分支，且开发提交都进了 `master`，
但**生产容器 checkout 的是 `v1.0`**，导致：

- `git pull origin master` 能拉到新代码，但 `git rev-parse HEAD` 显示的是 v1.0 的旧提交
- ATT 环境按 `v1.0` 构建，缺最新修复
- 排查时容易误判「代码没生效」

实测关系：`v1.0` 是 `master` 的**祖先**（`git merge-base --is-ancestor` 返回真），
master 比 v1.0 多 66 个提交，**无分叉、无冲突**。

### 8.2 统一做法

```bash
# 把 master 全部内容推到 v1.0（fast-forward，不产生 merge commit）
git push origin master:v1.0

# 本地同步
git checkout v1.0 && git reset --hard origin/v1.0 && git checkout master
```

结果：`master` / `v1.0` / `origin/master` / `origin/v1.0` 全部指向同一提交。

### 8.3 约定（避免再次分裂）

- **日常开发只推 `master`**
- 每次发布后执行一次 `git push origin master:v1.0` 保持同步
- 生产容器保持在 `v1.0` 分支（不切分支，减少意外）
- 打 tag 在 `master` 上打，v1.0 同步后自动可见

### 8.4 生产仓库本地改动要保留

`/path/to/amm` 上通常有这些**有意保留**的本地改动，
`git pull` 前不要 `checkout .` 掉：

```
M  backend/config/models_config.yaml     # 节点名/模型清单等运行时配置
?? data/                                 # 运行时数据库
?? templates/custom/                     # 用户自建模版
?? deploy/docker-compose.unraid.yml.bak-* # 部署备份
```

拉代码时用 `git stash -u` → `pull` → `git stash pop`。

## 九、Unraid 容器镜像构建（2026-11-17 实测）

完整的踩坑过程见 `docs/维护记录-20261117-Unraid容器重建.md`，
这里只留可直接照做的结论。

### 9.1 用哪个 Dockerfile

| 文件 | 何时用 |
|---|---|
| `deploy/Dockerfile.local-cuda` | **默认用这个**。用本地 CUDA 组件包，零外网下载 |
| `deploy/Dockerfile.unraid` | 只有在网络很好、且没有本地组件包时才用 |

```bash
cd deploy
cp ../backend/requirements.txt ./requirements.txt
docker build -f Dockerfile.local-cuda -t amm:rocky9-cu132 .
```

### 9.2 CUDA 组件包必须包含 5 类东西

```
cuda-bundle/
├── lib64/libcublas.so.13.4.1.3       ← CUDA::cublas target 需要
├── lib64/libcublasLt.so.13.4.1.3     ← 同上
├── lib64/libnvblas.so.13.4.1.3
├── lib64/libcudart.so.13.0.96        ← 运行时需要（最容易漏！）
├── include/cublas*.h                 ← 编译期需要
├── include/cccl/                     ← cmake 需要
├── bin/cicc                          ← nvvm 前端（缺了 nvcc 报 0x7f）
└── nvvm-lib/libnvvm.so*              ← nvvm 运行库
```

**最容易漏的是 `libcudart`** —— 它和 cublas 是不同的包，
只导 cublas 时镜像能构建、容器能起来、health 也绿，
但一启动模型就 `libcudart.so.13: cannot open shared object file`。

### 9.3 导出组件包必须用 `tar -ch`

```bash
docker exec AMM sh -c "cd /usr/local/cuda-13.2/lib64 && tar -chf - \
  libcublas.so.13.4.1.3 libcublasLt.so.13.4.1.3" > libs.tar
```

`-h` 解引用符号链接。用 `docker cp` 只会得到断链（大小 0 或指向不存在）。

### 9.4 构建上下文不能用 symlink

`ln -s` 指向上下文之外的目录，`docker build` 会报
`failed to compute cache key: "/cuda-bundle/xxx": not found`。
必须 `cp -r` 成真实目录（834MB，构建完可删）。

### 9.5 Dockerfile 里不要下大文件

`libcublas` 单个 RPM 就 158MB。Dockerfile 里的 `curl` 下载：
- 每次 build 从零开始，没有跨 build 的续传
- TLS 抖动直接让整个 build 失败（`curl: (56) SSL_read`）
- 缓存层失效就全量重来

**结论：超过几十 MB 的依赖用本地包**，别放 Dockerfile 里现场下载。

### 9.6 gi 容器名是大写

`docker restart amm` → `No such container`。正确的是 `docker restart AMM`。

### 9.7 docker inspect 输出 labels 的方式

某些 docker 版本 `{{json .Config.Labels}}` 返回空，改用：

```bash
docker inspect AMM --format '{{range $k,$v := .Config.Labels}}{{$k}}={{$v}}{{println}}{{end}}'
```

### 9.8 Unraid 图标必须是 raw 直链

```
✅ raw.githubusercontent.com/xztjhs/amm/master/frontend/assets/logo.png  (image/png)
❌ github.com/xztjhs/amm/blob/master/frontend/assets/logo.png           (text/html)
```

`/blob/` 是 HTML 页面，Unraid 拿不到图片。

### 9.9 判断 CUDA 真生效的唯一标准

```bash
nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader
```

里面必须有你的进程 PID。

以下三个都**不能**作为证据：
- `ldd llama-server | grep cudart` 显示已链接
- `llama-server --list-devices` 能列出 CUDA0
- 容器 `--runtime nvidia` 启动成功

缺 ggml 动态库（`libggml-cuda.so`）时会静默退回 CPU，
日志里连一行 CUDA 都不打，只有 nvidia-smi 能看出来。

### 9.10 运行时临时修补必须写回镜像

`docker cp` 塞库进运行中的容器能立刻跑通，但：
- Unraid 用模板重建容器 = 常见操作
- 重建后临时修补全部丢失，而且"上次明明好了"会让排查更慢

**任何手动修补，要么写进 Dockerfile，要么在文档里明确标注为临时手段。**

### 9.11 构建完成后的最小验收

```bash
# 1) 镜像内组件齐全
docker run --rm --entrypoint sh amm:rocky9-cu132 -c '
  ls /usr/local/cuda-13.2/lib64/libcudart.so.13 &&
  ls /usr/local/cuda-13.2/lib64/libcublas.so &&
  ls /usr/local/cuda-13.2/nvvm/bin/cicc &&
  python3.11 -c "import aiohttp,yaml,psutil" && echo ALL_OK'

# 2) 容器起得来
docker ps --filter name=AMM

# 3) 服务健康
curl -s http://127.0.0.1:60008/api/health

# 4) 模型能真跑（这条最重要，前三条都过了也可能挂在这）
```
