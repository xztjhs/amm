# 2026-11-17 Unraid 容器重建：踩坑与解法

> 背景：AMM 容器与镜像被清空（宿主机 19:12 重启过），需从零重建并按
> Unraid 标准容器（dockerMan）部署。本文记录过程中所有失败与最终方案。

## 二、第一次失败：NVIDIA 源下载断流

### 现象

用 `deploy/Dockerfile.unraid` 构建，卡在 CUDA RPM 下载：

```
#8 81.42 curl: (56) OpenSSL SSL_read: error:0A000126:
          SSL routines::unexpected eof while reading, errno 0
ERROR: failed to build: ... exit code: 56
```

Dockerfile 里的代码：

```dockerfile
for p in $pkgs; do
    curl -fsSL --http1.1 --retry 20 --retry-all-errors --retry-delay 2 \
         -C - -o "$f" "$CUDA_REPO/$f"
done
```

### 分析

- 需要下载 11 个 RPM，其中 `libcublas` 就有 158MB
- `--retry 20` + `-C -`（断点续传）都加上了，仍然反复失败
- 失败点是 TLS 层被断开，不是大小限制

### 结论

**从 NVIDIA 官方源拉大文件在这个网络环境下不可靠**。这不是代码问题，
重试次数再多也解决不了。必须换方案。

## 三、第二次失败：符号链接导致 COPY 失败

### 方案

从已有容器（`att/cuda-bundle`）导出了 CUDA 组件包，改用 `COPY` 替代下载。
为了省空间，先用 symlink 挂到构建上下文：

```bash
ln -sfn /path/to/cuda-bundle deploy/cuda-bundle
docker build -f Dockerfile.local-cuda -t amm:rocky9-cu132 .
```

### 现象

```
ERROR: failed to compute cache key: failed to calculate checksum of ref ...
  "/cuda-bundle/nvvm-lib": not found
```

### 原因

Docker build 计算构建上下文时**不跟随指向上下文之外的符号链接**
（安全设计，防止 COPY 出上下文边界）。

### 解决

改成真实目录复制：

```bash
rm -f deploy/cuda-bundle
cp -r /path/to/cuda-bundle ./cuda-bundle
```

代价：834MB 占双份。可接受（构建完可删）。

## 四、第三次失败（最隐蔽）：libcudart 缺失

### 现象

镜像构建成功、容器启动、服务 200、引擎识别正常。
但启动模型实例时：

```
/opt/amm-engines/llama_cpp/b12381-cuda/bin/llama-server:
  error while loading shared libraries: libcudart.so.13:
  cannot open shared object file: No such file or directory
```

实例状态 `ready: false`。

### 原因分析

前一版从 ATT 导出的组件包**只有 cublas 三件套**：

```
libcublas.so.13.4.1.3
libcublasLt.so.13.4.1.3
libnvblas.so.13.4.1.3
```

而 `libcudart`（CUDA Runtime）是**另一个包**，之前是从 RPM 装的，
导出时没带上。

### 为什么难发现

- `docker inspect` 看容器 Up、health healthy
- `/api/health` 返回 200
- `/api/engines/installed` 能列出 llama_cpp cuda
- 只有真正启动模型时才暴露

**教训：CUDA 依赖是否齐全，只有跑一次模型才知道。**

### 解决

1. 找到有 cudart 的容器（`mineru-api`，CUDA 13.0）
2. 导出 `libcudart.so.13.0.96`
3. 加入组件包 + Dockerfile 里补符号链接
4. 重建镜像

CUDA 13.0 的 `libcudart.so.13` 与 13.2 的 ABI 兼容，可以直接用。

### 临时验证 vs 最终修复

过程中我先用 `docker cp` 把库塞进运行中的容器，模型能跑了。
但**这样一按模板重建就失效** —— 库在容器可写层，不在镜像里。

所以做了第二遍：把 libcudart 打进组件包，重建镜像，然后
**删除容器、用新镜像重建，验证不手动补任何库就能跑**。

这一步才算真正完成。

## 五、最终方案

### 5.1 新增文件

| 文件 | 作用 |
|---|---|
| `deploy/Dockerfile.local-cuda` | 用本地组件包构建，不下载 RPM |
| `deploy/cuda-bundle/` | CUDA 组件（cublas + cudart + 头文件 + nvvm + cccl） |
| `deploy/unraid/my-AMM.xml` | dockerMan 模板（17 个配置项） |

### 5.2 Dockerfile 关键点

```dockerfile
# 1. 不装 curl（与 Rocky 9 的 curl-minimal 冲突）
# 2. 装 gcc-toolset-12（CUDA 13 不认 gcc 11.5）
RUN dnf install -y ... gcc-toolset-12 gcc-toolset-12-gcc-c++ ...

# 3. COPY 组件包
COPY cuda-bundle/lib64/    /usr/local/cuda-13.2/lib64/
COPY cuda-bundle/include/  /usr/local/cuda-13.2/include/
COPY cuda-bundle/bin/      /usr/local/cuda-13.2/nvvm/bin/
COPY cuda-bundle/nvvm-lib/ /usr/local/cuda-13.2/nvvm/lib64/

# 4. 补符号链接（组件包只带真实版本文件）
RUN ... for f in libcublas libcublasLt libnvblas; do
        ln -sf "${f}.so.13.4.1.3" "${f}.so.13"
        ln -sf "${f}.so.13" "${f}.so"
    done;
    # cudart 单独处理（版本号不同）
    if [ -f libcudart.so.13.0.96 ]; then
        ln -sf libcudart.so.13.0.96 libcudart.so.13
        ln -sf libcudart.so.13 libcudart.so
    fi;
    ldconfig
```

### 5.3 构建

```bash
cd /path/to/amm/deploy
cp ../backend/requirements.txt ./requirements.txt
docker build -f Dockerfile.local-cuda -t amm:rocky9-cu132 .
```

耗时 3-5 分钟，零外网下载。

## 六、Unraid 标准容器部署

### 6.1 三个必须的 label

```bash
-l net.unraid.docker.managed=dockerman
-l "net.unraid.docker.icon=https://raw.githubusercontent.com/xztjhs/amm/master/frontend/assets/logo.png"
-l "net.unraid.docker.webui=http://[IP]:[PORT:80]"
```

**图标必须用 raw 直链**：

```
✅ https://raw.githubusercontent.com/xztjhs/amm/master/frontend/assets/logo.png   (200, image/png)
❌ https://github.com/xztjhs/amm/blob/master/frontend/assets/logo.png            (200, text/html)
```

`/blob/` 返回的是 HTML 页面，Unraid 拿不到图片。

### 6.2 自愈

```bash
--restart unless-stopped
--health-cmd "python3.11 -c '...urllib.../api/health...'"
--health-interval 30s --health-timeout 6s --health-retries 3
```

> 注意：`--health-cmd` 里嵌套引号很容易写坏。我第一版写了很绕的
> `chr(104)+chr(116)...` 拼接（为了避开引号冲突），能工作但可读性差。
> 更干净的做法是 `--health-cmd 'curl -f http://127.0.0.1/api/health'`，
> 但镜像里没装 curl（与 curl-minimal 冲突），所以还是用 python。

### 6.3 验证

```bash
docker ps --filter name=AMM
# 期望：AMM | Up (healthy) | amm:rocky9-cu132

docker inspect AMM --format '{{range $k,$v := .Config.Labels}}{{$k}}={{$v}}{{println}}{{end}}'
```

**注意 `--format '{{json .Config.Labels}}'` 在这个 docker 版本下返回空**，
要改用上面这种逐个输出的写法。

## 八、经验总结

### 8.1 判断「CUDA 是不是真能用」的唯一标准

**不是** `ldd` 显示链接了 cudart，**不是** `--list-devices` 列出 GPU，
**也不是** `nvidia-smi` 看到了容器。

是这条：

```bash
nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader
```

里面有你的进程 PID，才算真的跑在 GPU 上。
缺 ggml 动态库时会**静默退回 CPU**，日志里连一行 CUDA 都不打。

### 8.2 临时修复必须落进镜像

用 `docker cp` 往运行中的容器塞文件能立刻见效，但：
- 容器重建就没了
- Unraid 用模板重建容器 = 必然发生
- 下次出问题会更难查（"上次明明好了"）

**任何运行时手动修补，要么写进 Dockerfile，要么明确记录为临时手段。**

### 8.3 大文件下载不适合放进 Dockerfile

Dockerfile 里的 `curl` 下载：
- 没有断点续传的持久化（每次 build 从零开始）
- 网络抖动直接导致整个 build 失败
- 缓存层失效就全量重来

**体积超过几十 MB 的外部依赖，改用本地包 / 私有 registry / 构建缓存。**

### 8.4 Unraid 容器名的坑

容器名是 `AMM`（大写）。`docker restart amm` 报
`No such container`，容易误以为容器丢了。
