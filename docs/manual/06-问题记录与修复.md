## 6.0 修问题方法论（先记住）

在 AMM 排查问题时总是按这个顺序：
1. **看日志**：Dashboard → 相关模型 → Logs tab（或 `/amm/logs/<model>_server.log`）
2. **看状态**：`GET /api/instances` 看 status/pid/gpu_memory
3. **看进程**：容器内 `ps aux | grep <engine>`，`nvidia-smi` 看显存
4. **复现**：用 第 3/4 章的 API 单条调用复现，缩小范围
5. **看代码**：`backend/api/*.py` 找到对应处理器读日志与分支

## 6.1 已修复问题清单（按版本）

### 🔧 v0.7.3（Diffusers 高级参数 / 显存 / Playground）

**P1：Models 页 diffusers Advanced 区不显示**
- **现象**：T2I/T2V/I2V 的高级参数区渲染为空。
- **根因**：`renderAdvancedSettings` 是 async 函数，却在同步模板字面量 `${...?renderAdvancedSettings(id):''}` 被求值，拿到的是 Promise → 渲染空。
- **修复**：模板先渲染占位 `<div id="adv-wrap-<id>">`，渲染完成后对 engine=diffusers 的模型异步注入真实区，并 `bindParamChange` 联动显存估算。
- **验证**：三类模型 Advanced（Quant/Compute/Offload/Boundary/CPU-Offload）均正常。

**P1：offload 下拉不读模型实际值**
- **根因**：下拉初始值未从模型 yaml 读取。
- **修复**：读取并回写模型实际 offload 配置。

**P2：每次推理后 GPU 显存不释放**
- **根因**：diffusers pipeline 缓存进 server 进程常驻 GPU。
- **修复**：t2i/t2v/i2v 完成/异常共 6 处自动释放（`del pipe + gc + 清 pipeline cache + empty_cache`）。实测推理 55.9G → 完成后 655M。

### 🔴 v0.7.1 容器 supervisor 化 + diffusers 独立启停
- **现象**：容器内 `kill server` 居然把容器杀了。
- **根因**：entrypoint `exec python server.py` 使 server 成为 PID1 → kill 即杀容器。
- **修复**：entrypoint 改 supervisor（PID1=wrapper），Trap 转发信号，server 后台子进程、退出自动重启（`AMM_RESTART_DELAY` 调）。
- **连带**：新增 `POST /api/bridge/diffusers/preload|unload` + `deploy/diffusers_ctl.sh`，diffusers 推理与 Web 主服务解耦。

### 🔴 v0.7：Diffusers 四问（日志空 / GPU 不工作 / 下载 / 计时）
- **P1 Logs 为空**：diffusers 用内置桥接（非子进程），`build_command` 返回空 → 无日志文件。修复：`diffusers_bridge` 每模型写 `logs/<model>.server.log`。
- **P2 video 不工作（GPU 利用趋0）**：`cpu_offload` 走序列 CPU offload，层被挪 CPU。修复：offload 策略显式化（`offload: gpu|model|group`），gpu=全驻显存。
- **P3 下载**：下载进度统计只统计目标子目录；停滞检测 180s 防慢代理误杀。

### 🔴 v0.6.x：引擎问题
- **vLLM 参数缺陷**：`quantization=auto` 被 vLLM 拒绝（Unknown quantization method: auto）。修复：auto/空不传。
- **Diffusers import 失败**：AMM server 是系统 python，diffusers 依赖却在 vLLM venv。修复：把 numpy/diffusers/transformers 等装到系统 python。
- **I2V 加载失败**：硬编码 `variant="bf16"` 但 I2V 无 bf16 文件 → 自动检测。
- **vLLM stop/restart 子进程残留**：`VLLM::EngineCore` setsid 脱离进程组。修复：engine 停止改为**递归进程树清理**（psutil.children 递归 + /proc 兜底），SIGTERM 后 SIGKILL 回收。

### 🟡 更早期
- vLLM 进程树 `kill -9` 兜底（待永久修复）。
- Embedding 收敛为 llama_cpp（vLLM embedding 参数难调）。
- llama_cpp 空回复根因：Qwen3 思考 + `--reasoning-budget` 缺失 → 加 reasoning_budget 防空回复（详见 `docs/llama_cpp-空回复-rootcause-20260808.md`）。

## 6.2 本次 v0.8.0 检修发现的问题

### ❗ Bug：版本号过时（v0.2 显示错误）
- **现象**：页脚与 Settings 页显示 `AMM v0.2`，但实际功能已是 v0.7.x / 即将 v0.8.0。
- **根因**：版本号硬编码未随迭代更新。
- **修复**：统一版本常量，前端页脚 + Settings 从后端读取当前版本（见 6.3 修复方案）。

### ❗ 观察：容器体量膨胀（运维类）
- 容器写层累计 ~16G（pip/vLLM 缓存 + tmp + 日志 + 旧备份）。
- **修复（已完成）**：清理 pip 缓存 11G、vLLM 缓存、/tmp 2.1G、日志 918M、备份目录；写层降至 220M。
- 详见 `docs/维护记录-20260809-容器清理与部署配置.md`。

## 6.3 版本号修复（v0.8.0 一并合入）

目标：让**页脚**与 **Settings** 显示真实版本 `v0.8.0`，且后续版本只需改一处。

**方案**：
1. 在 `backend/config/` 增加或沿用版本常量 `AMM_VERSION = "v0.8.0"`。
2. `GET /api/settings` 返回 `version` 字段（已存在，但值需改为 0.8.0 或读取常量）。
3. `frontend/index.html` 页脚 + `frontend/js/app.js`：加载 `/api/settings` 后用返回的 version 替换页脚 `AMM v0.2`。
4. 同步 `CHANGELOG.md` 新增 v0.8.0 条目。

> 修复代码后需验证：刷新页面 → 页脚显示 `AMM v0.8.0`，Settings 版本显示 `v0.8.0`。

## 6.4 运维速查（问题排查命令）

以下命令在 **AMM 容器内**执行（root）：

```bash
# AMM 服务健康
curl -s http://127.0.0.1:80/api/health

# 模型状态
curl -s http://127.0.0.1:80/api/instances | head -c 2000

# 看某个模型的日志
tail -50 /amm/logs/chat_server.log

# 看 GPU
nvidia-smi

# 手动启停某模型
curl -s -X POST http://127.0.0.1:80/api/instances/chat/start
curl -s -X POST http://127.0.0.1:80/api/instances/chat/stop

# diffusers 显存立即释放
curl -s -X POST http://127.0.0.1:80/api/bridge/diffusers/unload
```
