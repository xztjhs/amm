# 第 8 章 故障排查

> 版本：v1.9 ｜ 更新日期：2026-11-17
> 按「症状 → 原因 → 处理」组织。遇到问题先在这里按症状找。

## 8.1 快速自检五步

任何异常，先按顺序跑这五步，能定位 80% 的问题：

```bash
# ① 容器活着吗
docker ps -a --filter name=AMM

# ② 服务接口通吗
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:60008/api/health

# ③ 日志有报错吗
docker exec AMM tail -50 /amm/logs/amm_server.log

# ④ GPU 能用吗
docker exec AMM nvidia-smi

# ⑤ 磁盘满了吗
df -h /path/to/amm
```

## 8.2 服务起不来 / 页面打不开

### 症状：`curl /api/health` 无响应或连不上

**可能原因与处理：**

| 原因 | 确认方法 | 处理 |
|---|---|---|
| 容器没运行 | `docker ps -a` 显示 `Exited` | `docker start AMM` |
| 端口没映射 | `docker port AMM` | 重建容器，加 `-p 60008:80` |
| 端口被占用 | `ss -ltn \| grep 60008` | 换端口或停掉占用进程 |
| 服务进程崩了 | 容器 Up 但无响应 | `docker exec AMM ps aux \| grep server.py` |
| 启动报错 | 看 `amm_server.out` | 按报错处理（见下） |

### 症状：容器 `Exited (0)` 或 `Exited (255)`

**这是最常见的「服务莫名消失」原因。**

```bash
docker inspect AMM --format 'Exit={{.State.ExitCode}} At={{.State.FinishedAt}} Policy={{.HostConfig.RestartPolicy.Name}}'
```

| ExitCode | 含义 | 处理 |
|---|---|---|
| `0` | 被正常停止（人工或脚本发的 SIGTERM） | `docker start AMM` |
| `255` | 异常退出 | 看日志；确认 `RestartPolicy` |
| `137` | 被 OOM killer 杀掉 | 减小模型/降低并发，见 8.6 |

**根本解决**：确认重启策略是 `unless-stopped`

```bash
docker inspect AMM --format '{{.HostConfig.RestartPolicy.Name}}'
# 如果是 no：
docker update --restart unless-stopped AMM
```

> 实测教训：宿主机的 `uptime` 显示刚重启过（`last reboot`），
> 而容器策略是 `no` → 容器不会自己回来，服务就"消失"了。

## 8.3 模型启动失败

### 症状：点启动后状态变 error，或提示「模型 xxx 未启动」

**第一步：看实例日志**

```bash
docker exec AMM tail -50 /amm/logs/<实例UID>_server.log
```

或在 Dashboard 点模型名 → 看日志。

### 常见报错对照表

| 日志里的关键字 | 原因 | 处理 |
|---|---|---|
| `error while loading shared libraries: libcublas.so.13` | CUDA 库缺失 | 跑 `bash /amm/deploy/cuda_components.sh` |
| `--error 0x7f` | 缺 nvvm（cicc） | 同上，缺 nvvm 组件 |
| `cublas_v2.h: No such file` | 缺 cublas 头文件 | 同上 |
| `No such file or directory` + 模型路径 | 模型文件不存在 | 检查 `/models` 下是否真有该文件 |
| `failed to load model` | 模型文件损坏/格式不对 | 重新下载；确认是 GGUF 而非 safetensors |
| `Address already in use` | 端口被占 | 换实例端口，或停掉占用者 |
| `out of memory` / `CUDA error: out of memory` | 显存不足 | 降 `n_gpu_layers`、减 `ctx_size`、换小模型 |
| `does not support embeddings` | 实例没开 embeddings | 类别选 embedding，或参数里勾 `embeddings=true` |
| `context size too large` | ctx_size 超模型上限 | 降到模型支持的范围（看模型说明） |

### 症状：启动成功但请求返回 500

**v1.9 之前**：launch 返回 running 时端口还没就绪，立刻请求会 500。
**v1.9 起**：launch 会等端口真正可用才返回（返回里带 `ready: true`）。

如果你还在老版本：

```bash
# 手动确认端口通了再发请求
for i in $(seq 1 30); do
  (echo > /dev/tcp/127.0.0.1/18100) 2>/dev/null && break
  sleep 1
done
```

## 8.4 GPU 相关

### 症状：模型跑起来了，但 GPU 上找不到进程（最隐蔽）

**判断依据只能是 nvidia-smi，不能看 `--list-devices`**：

```bash
nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader
```

如果这里没有你的进程，但 `llama-server --list-devices` 能列出 GPU，
说明**动态后端库缺失，运行时静默退回了 CPU**。

**确认：**

```bash
docker exec AMM ls /usr/local/bin/libggml-cuda.so
# 不存在 → 就是这个原因
```

**处理：** 重新安装 llama.cpp，确保 `.so` 一起拷贝：

```bash
cp -a build/bin/*.so* /usr/local/bin/
ldconfig
```

`deploy/install.sh` v1.9 起已修复此问题。

### 症状：显存不够

**先看谁占了显存：**

```bash
nvidia-smi
# 或看 Dashboard 的「正在运行的程序」
docker exec AMM ps aux | grep llama-server
```

**处理手段（按优先级）：**

1. 停掉不用的实例（Models → 运行中实例 → Stop）
2. 降低 `n_gpu_layers`（少放几层到 GPU，其余用 CPU）
3. 减小 `ctx_size`（上下文越长，KV cache 越占显存）
4. 换更小的量化（Q8_0 → Q4_K_M）
5. 开 `KV cache 量化`（参数：cache_type_k/v 设为 q8_0）

### 症状：`/api/system` 或 `/api/gpu` 很慢（几秒以上）

根因是 `nvidia-smi` 子进程调用阻塞事件循环。
v1.9 已加 2 秒缓存，若仍慢说明 GPU 处于异常状态：

```bash
docker exec AMM nvidia-smi    # 手工跑，看是否也慢
```

如果手工也慢，是驱动或 GPU 硬件状态问题，重启宿主机或 `nvidia-smi -r`。

## 8.5 API 调用问题

### 症状：401 Unauthorized

**先看响应体的 `type` 字段，区分来源：**

| 响应体 | 来源 | 处理 |
|---|---|---|
| `{"type":"auth_error"}` | AMM 自己的鉴权 | 带正确的 Key，或关闭鉴权 |
| `{"type":"upstream_error"}` | 上游 provider | 检查 provider 的 Key / base_url |

**AMM 鉴权的特殊情况**：即使你"清除了默认 Key"，如果还签发过虚拟 Key，
鉴权仍会保持开启（安全设计：防止旧 Key 持有者突然获得无鉴权访问）。

真正退回免鉴权：**Settings → 完全关闭鉴权**（需输入 YES 确认）。

### 症状：404 model not found

```bash
curl -s http://localhost:60008/v1/models | python3 -m json.tool
```

看你要用的模型 ID 在不在列表里。

- 不在 → 实例没运行，或没签发对应 Key 的模型权限
- 在但调用 404 → 检查 `model` 字段拼写是否完全一致（含大小写，v1.8 起大小写不敏感）

### 症状：客户端显示的模型名不对（如 qwen3 显示成 "Qwen3 14B"）

**原因**：Cherry Studio 这类客户端会拿模型 ID 去"模型名注册表"做归一化匹配。
`qwen3` 去掉参数尺寸后缀后命中 `qwen3-14b`，名称和能力都会被覆盖。

**处理**：把实例 UID 改成带类别身份的完整名字：

```
❌ qwen3
✅ qwen3-embedding-0.6b
```

v1.9 起向导会自动生成正确的 UID 并实时提示风险。

### 症状：流式调用在「调用历史」里看不到输出

v1.9 已修复。如果还是 `(stream)`，确认版本：

```bash
curl -s http://localhost:60008/api/settings | grep -o '"version":"[^"]*"'
```

## 8.6 性能与资源

### 症状：容器被 OOM 杀掉（Exit 137）

```bash
docker inspect AMM --format '{{.State.OOMKilled}}'
dmesg | grep -i 'killed process'
```

**处理**：

- 同时运行的大模型太多 → 减少实例
- 减小 `ctx_size`（KV cache 是内存大头）
- 给容器设内存上限，让它优雅失败而不是拖垮宿主机：
  ```bash
  docker update --memory 48g --memory-swap 48g AMM
  ```

### 症状：日志文件暴涨

```bash
docker exec AMM ls -lh /amm/logs/amm_server.log*
```

v1.9 起已启用轮转（默认 50MB × 5）。如果仍是单个大文件，说明版本较老。

调整大小：

```bash
-e AMM_LOG_MAX_BYTES=104857200   # 100MB
-e AMM_LOG_BACKUPS=3
```

也可以临时清理：Log Center → 🧹 清理。

### 症状：页面卡、响应慢

刷新间隔设得太短（0.1s）会让前后端压力很大。

到右上角把刷新间隔调到 **2s 或 5s**。

## 8.7 引擎与依赖

### 症状：引擎列表加载很慢（7 秒以上）

根因是统计引擎目录体积时 `rglob` 扫全部文件（vLLM 的 venv 有 8 万+ 文件）。
v1.9 已加 mtime 缓存 + 启动预热，正常应 **< 10ms**。

如果仍然慢：

```bash
curl -s -o /dev/null -w '%{time_total}\n' http://localhost:60008/api/engines/installed
```

超过 1 秒说明缓存没生效，检查版本是否 >= v1.9。

### 症状：引擎安装失败

```bash
# 看任务日志
curl -s http://localhost:60008/api/engines/tasks | python3 -m json.tool
```

常见原因：

| 原因 | 处理 |
|---|---|
| pip 源不通 | Settings → PyPI 镜像源，换成可用镜像 |
| 磁盘满 | `df -h` |
| 编译缺依赖 | `bash deploy/install.sh` 重装系统依赖 |
| 网络断流 | 重试；大包建议先手动下载 |

### 症状：pip 下载很慢

Settings → PyPI 镜像源 → 选 `mirrors.aliyun.com` 或 `pypi.tuna.tsinghua.edu.cn`。

## 8.8 数据与配置

### 症状：重启后实例配置丢了

实例定义存在 SQLite：

```bash
docker exec AMM python3 -c "
import sqlite3
c = sqlite3.connect('/amm/data/amm.db')
for r in c.execute('select uid,status from instances'):
    print(r)
"
```

如果 `data/` 目录没做持久化挂载，容器重建会丢。确认：

```bash
docker inspect AMM --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}'
```

应该有 `data` 目录的挂载。

### 症状：改了配置不生效

- `models_config.yaml` 改动 → Settings → **重载配置**
- 目录配置、环境变量改动 → **重启服务**

### 症状：`git pull` 说本地有改动无法合并

生产目录通常有这些有意保留的本地改动：

```bash
git stash -u
git pull origin v1.0 --ff-only
git stash pop
```

**不要** `git checkout .`，会把你的节点名、自建模版冲掉。

## 8.9 前端问题

### 症状：页面白屏 / 所有面板都点不开

**打开浏览器开发者工具（F12）→ Console，看有没有红色报错。**

2026-11-17 实测过一次：前端模块化拆分后，`window.xxx = xxx` 残留导致
`ReferenceError`，整个初始化中断，页面全白但接口都正常。

v1.9 已修复。如果遇到：

```bash
# 强刷清缓存
Ctrl+Shift+R
# 或检查静态资源版本号
curl -s http://localhost:60008/ | grep 'js/app.js'
```

### 症状：升级后界面还是旧的

浏览器缓存。强制刷新（Ctrl+Shift+R），或确认 HTML 里的版本号已更新
（v1.9 是 `?v=2.0`）。

### 症状：文件管理器显示"加载中"不动

v1.9 修复了初始化时机问题。如果还出现，检查接口：

```bash
curl -s 'http://localhost:60008/api/fm/roots'
```

返回 200 说明后端正常，是前端初始化没触发（刷新页面）。

## 8.10 排错常用命令速查

```bash
# 容器
docker ps -a --filter name=AMM
docker inspect AMM --format 'Exit={{.State.ExitCode}} Policy={{.HostConfig.RestartPolicy.Name}}'
docker logs --tail 50 AMM
docker restart AMM

# 服务
curl -s http://localhost:60008/api/health
curl -s http://localhost:60008/api/settings
docker exec AMM tail -100 /amm/logs/amm_server.out

# 实例
curl -s http://localhost:60008/api/instances | python3 -m json.tool
docker exec AMM ls /amm/logs/*_server.log
docker exec AMM tail -50 /amm/logs/<uid>_server.log

# GPU
nvidia-smi
nvidia-smi --query-compute-apps=pid,used_memory --format=csv
docker exec AMM nvidia-smi

# 磁盘/内存
df -h
free -g
docker stats --no-stream AMM

# 数据库
docker exec AMM python3 -c "
import sqlite3; c=sqlite3.connect('/amm/data/amm.db')
print(list(c.execute('select uid,category,port,status from instances')))"

# 引擎
curl -s http://localhost:60008/api/engines/installed | head -c 500
docker exec AMM ls /opt/amm-engines/<engine>/
```

## 8.11 还是解决不了？

按这个顺序收集信息，能大幅提高排查效率：

1. **版本**：`curl -s .../api/settings | grep version`
2. **症状**：什么操作、什么报错（截图 + 文字）
3. **日志**：`amm_server.log` 尾部 50 行 + 对应实例的 `_server.log`
4. **环境**：`docker inspect` 的 Env 与 Mounts
5. **GPU**：`nvidia-smi` 完整输出

把这五项一起发出来，基本能直接定位。
