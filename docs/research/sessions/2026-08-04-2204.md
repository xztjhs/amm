## OCR 卡住根因：Task Executor 被 OOM Kill 反复杀掉

### 核心问题

RAGFlow 容器 **内存已达 91.5%（10.98G / 12G 限制）**，且 `OOMKilled = true`。

日志中 task_executor 被杀了 **259 次**，全部是 `Killed`（SIGKILL），这是 Docker 因容器超出 `mem_limit: 12g` 而杀进程。

### 为什么会 OOM？

1. **OCR 模型用 CPU 跑 ONNX**：日志显示 `load_model ... uses CPU`。虽然机器有 GPU（RTX 6000D），但 `CUDA_VISIBLE_DEVICES` 环境变量为空，导致 ONNX 推理走 CPU 而非 GPU。CPU 推理内存消耗大。

2. **8 个 worker 并发**：compose 里 `--workers=8`，每个 worker 都要加载 ONNX 模型（det + rec + layout + tsr），每个进程约 1-2G 内存，8 个 worker 轻松超过 12G 限制。

3. **被杀后自动重启 → 再次被杀**：entrypoint.sh 检测到 worker 退出后自动重启，但内存还是不够，形成 **启动→加载模型→OOM Kill→重启** 的死循环。这就是为什么文件一直卡在 "OCR started" 永远完不成。

### 解决方案（按推荐顺序）

**方案一：让 OCR 用 GPU（推荐）**

在 docker-compose.yml 的 ragflow 服务环境变量中添加：
```yaml
- CUDA_VISIBLE_DEVICES=0
- NVIDIA_DISABLE_REQUIRE=1
```
同时需要给容器 GPU 访问权限，添加：
```yaml
deploy:
  resources:
    reservations:
      devices:
        - driver: nvidia
          count: 1
          capabilities: [gpu]
```

**方案二：减少 worker 数量 + 增加 mem_limit**

```yaml
command:
  - --workers=2      # 8 → 2
mem_limit: 20g       # 12g → 20g（机器有 692G 内存）
```

**方案三：仅增加 mem_limit（最快）**

```yaml
mem_limit: 32g       # 给够内存让 CPU 推理也能跑
```
