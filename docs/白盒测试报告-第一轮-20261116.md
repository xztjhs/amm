## 二、失败项（真实缺陷）

### P1 · D3：`/api/engines/installed` 响应 7-13 秒

- **用例**：L1-09
- **现象**：每次调用耗时 6.97–13.27 秒
- **根因**：`engine_catalog.installed_versions()` 对每个引擎目录执行 `entry.rglob("*")` 逐文件累加大小，沙箱里合计约 **19 万个文件**（vLLM 8.9 万 / diffusers 4.6 万 / sentence-transformers 4 万），且无缓存
- **影响**：启动向导每渲染一次就调它，用户看到的是"向导卡住十几秒"
- **修复方向**：体积统计改为惰性/缓存（见 §四 OPT-1）

### P2 · D1：GPU Monitor 页不可达

- **用例**：G-06
- **现象**：`<section id="tab-gpu">` 和 `renderGPU()` 都存在，但导航栏没有 `data-tab="gpu"` 入口，`zzGoto('gpu')` 也无法命中
- **影响**：整页功能对用户不可见（死代码）
- **修复方向**：加导航入口，或把 GPU 页并入 Dashboard（见 §四 OPT-2）

### P2 · D2：Playground「API Debug」面板不可达

- **用例**：L1-30
- **现象**：`<div id="pg-api">` 存在且含 Call API 按钮，9 个 `.pg-tab` 里没有指向 `data-pg="api"`
- **影响**：调试功能不可用
- **修复方向**：补一个页签（见 §四 OPT-2）

### P2 · DEV-04：前端"模型名称"建议值与 UID 完全相同

- **用例**：W-04
- **现象**：选 `Qwen3-Embedding-0.6B-Q8_0.gguf` 后，UID 建议 `qwen3-embedding-0.6b`，名称建议**也是** `qwen3-embedding-0.6b`
- **根因**：前端 `wizSuggestName()` 复用了 `wizModelIdentity()` 的**小写化**结果；后端 `derive_display_name()` 会保留原始大小写（`Qwen3-Embedding-0.6B`）
- **影响**：违背了"名称与 UID 不同客户端才会保留我们的名字"这条设计（Cherry Studio 兼容性直接受损）
- **修复方向**：前端名称建议改用保留大小写的派生（见 §四 OPT-3）

## 四、优化方案

### OPT-1（P1）引擎列表体积统计缓存

**目标**：`/api/engines/installed` 从 7-13s 降到 <200ms。

```python
# engine_catalog.py
_SIZE_CACHE: dict[str, tuple[float, float]] = {}   # path -> (mtime, size_mb)

def _dir_size_mb_cached(entry: Path) -> float:
    key = str(entry)
    try:
        mtime = entry.stat().st_mtime
    except OSError:
        return 0.0
    hit = _SIZE_CACHE.get(key)
    if hit and hit[0] == mtime:
        return hit[1]
    total = 0
    for p in entry.rglob("*"):
        try:
            if p.is_file():
                total += p.stat().st_size
        except OSError:
            pass
    size = round(total / (1024 * 1024), 1)
    _SIZE_CACHE[key] = (mtime, size)
    return size
```

再加一层 TTL 缓存（60s）包住整个 `installed_versions()`，并给 `/api/engines/installed` 加 `?nocache=1` 逃生口。

### OPT-2（P2）两个孤儿页面接线

- `index.html` 导航补 `<a class="nav-item" data-tab="gpu">GPU Monitor</a>`
- Playground `.playground-tabs` 补 `<button class="pg-tab" data-pg="api">🔌 API</button>`
- 同时补 L1 断言：导航项数 == section 数，消除这类"有实现无入口"

### OPT-3（P2）前端名称建议保留大小写

```js
function wizSuggestName(category, modelFile) {
  let name = wizModelIdentityRaw(modelFile);   // 不 .toLowerCase()
  if (!name) return '';
  if (category && category !== 'chat' && !name.toLowerCase().includes(category))
    name += ' (' + category + ')';
  return name;                                  // → "Qwen3-Embedding-0.6B (embedding)"
}
```

### OPT-4（P1）日志轮转

实测 `amm_server.log` 已 174MB，0.5s 轮询贡献 ~30MB/小时。建议 `RotatingFileHandler(maxBytes=50MB, backupCount=5)`，或 cron 每日切割 + gzip。

### OPT-5（P0）容器自愈

当前 `RestartPolicy=no`、无 HEALTHCHECK。今天两次容器退出（11:31 Exit=0、14:10 Exit=255）都无人知晓。

```bash
docker update --restart unless-stopped AMM
```
并在 `Dockerfile.unraid` 加：
```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD curl -fsS http://127.0.0.1/api/health || exit 1
```

### OPT-6（P2）模块体积收敛

`frontend/js/app.js` 已 5095 行单文件。建议按 tab 拆成 `js/tabs/*.js`，`index.html` 用 `<script type="module">` 引入。不改功能，只为可维护性与后续测试定位。

## 五、故障处理方案

### F1 · 容器退出无感知

- **检测**：`HEALTHCHECK` + `--restart unless-stopped`
- **确认**：`docker inspect AMM --format '{{.State.ExitCode}} {{.State.FinishedAt}}'`
  - Exit=0 → 被正常 stop（人工或脚本）
  - Exit=255 / 137 → 异常（137 = OOM kill，查 `dmesg | grep -i oom`）
- **处置**：`docker start AMM`，然后检查 `/amm/logs/amm_server.out` 尾部

### F2 · CUDA 库缺失（`libcublas.so.13: cannot open shared object`）

- **成因**：镜像本身不含 cublas，生产容器的 `/usr/local/cuda-13.2/lib64` 是容器写层里后装的；新建容器（如沙箱）拿不到
- **处置**：
  ```bash
  # 从能跑的容器导出（注意 tar 会解符号链接，docker cp 不会）
  docker exec AMM sh -lc "cd /usr/local/cuda-13.2 && tar -chf - lib64" > lib.tar
  tar -xf lib.tar -C <目标目录>
  # 运行时挂载：-v <目标目录>/lib64:/usr/local/cuda-13.2/lib64:ro
  ```
- **根治**：把 CUDA 运行库固化进镜像（见 §六 第二轮）

### F3 · `/api/system` 偶发长时间阻塞（实测曾 39 秒）

- **成因**：`get_gpu_info()` 同步调用 `nvidia-smi` 子进程和 GPUtil，卡住 aiohttp 事件循环；虽有 2s 缓存，冷启动或 GPU 忙时仍会阻塞
- **处置**：改用 `asyncio.to_thread()` 包住，或把 GPU 采集挪到后台定时任务写缓存
- **验证**：L3-06 已覆盖（40s 高频轮询，当前 p95 = 待补数据）

### F4 · 鉴权状态"回不去"

- **现象**：签发过虚拟 Key 后再全部吊销，`auth_enforced` 仍为 true，客户端继续 401
- **这是刻意的安全设计**（防止旧 Key 持有者突然获得无鉴权访问），**不是 bug**
- **正确做法**：Settings → 清除默认 Key（`clear_default_key` 会在无 Key 时清 `auth_enforced`）
- **待决策**：是否在 UI 上给一个明确的"完全关闭鉴权"按钮并二次确认

### F5 · 启动后瞬时 500

- **现象**：实例刚 `launch` 完立刻请求会 500（端口未就绪）
- **处置**：客户端应轮询 `/api/instances/{id}` 到 `status=running` 且端口可连；AMM 侧可考虑在 `launch` 返回前阻塞到端口 ready（最多 N 秒）

### F6 · provider base_url 丢失导致把 Key 发错地方

- **现象**：本轮真实踩到 —— icompify 的 Key 被发到 `api.openai.com`，返回 401 且报错信息指向 OpenAI
- **成因**：`upsert_provider` 对已存在 provider 用 `cfg.get("base_url") or cur.get(...)`，若某次保存没带 base_url 就会保留旧值；新建时若类型选 openai 且未填 base_url，会落到默认 openai 地址
- **处置**：`GET /api/providers/{name}` 确认 base_url；`POST` 时显式带上正确 base_url
- **改进建议**：在 UI 的 Provider 表格里把 base_url 与 type 默认值不一致的情况标黄
